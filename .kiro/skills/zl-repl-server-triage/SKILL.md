# repl-server triage

判定原则以 `docs/triage.md` 为准，决策记录在 `docs/triage-log.md`。本 skill 只做流程入口，不复制原则全文。

## 流程

1. **先收集告警**：分析范围不只请求和工具失败；同时检查系统告警与异常事件——`memory_warning`、`report`、`protocol_dropped`、`payloadDropped`、`tool_test` 失败、`script_saved` 失败。告警和请求失败一样是发现来源，不能只等用户报障。
2. **判归属**：本仓库代码/契约/文档/审计数据才在本仓库处理；外部 MCP server 响应、上游 4xx 根因转对应仓库；客户端行为只记录；协议设计内行为只补文档。
3. **过证据门槛**：要有可复现证据（日志计数 + 时间点，或源码 `文件:行号`）；只有推测的归 `INVESTIGATE`。
4. **分类**：
   - `FIX`：契约/文档与实现不一致且已造成真实失败、审计数据丢失、安全或数据正确性、协议兼容性拒绝真实客户端、核心功能不可用。
   - `IMPROVE`：本仓库、低风险、有测试、可改善可诊断性或使用效率，且不改外部契约。
   - `DOCUMENT`：行为本身是设计内或已修复，只是文档缺失或误导。
   - `IGNORE`：根因在外部、无实际收益，或维护成本大于收益；必须写理由。
   - `INVESTIGATE`：证据不足，先补观测或复现。
5. **查台账再动手**：同类问题先查 `docs/triage-log.md`；已 `IGNORE` 的除非出现新证据不再提。
6. **落盘**：每次分析后把每条发现写成日期 + 来源 + 表格（问题 / 分类 / 证据 / 决策 / 理由 / 状态）；状态变化更新原行。

## 授权边界

`FIX` / `IMPROVE` 且满足「本仓库内、有可复现证据、改动带测试、不破坏外部契约、不引入新依赖、单次可回滚」时，可以直接改代码/测试/文档并跑验证。

commit、push、重启 live 服务、跨仓库改动、数据迁移一律先问用户。不满足条件的只报告，不动手。
