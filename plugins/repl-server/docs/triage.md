# 分析发现的判定原则

- 状态：v1 契约；适用于 repl-server 的日志、请求记录、审计数据与问题报告
- 关联：`docs/triage-log.md`（决策台账）；执行入口是项目级 skill `zl-repl-server-triage`（`.kiro/skills/`，经 `.claude/skills` 软链供 Claude Code 使用，不安装到全局）

本文件回答一个问题：分析出的每条问题，该直接修、补文档、记录转派还是忽略。判定顺序固定为责任边界 → 证据门槛 → 分类 → 授权检查。

## 1. 责任边界

先判归属，再判严重程度。不属于本仓库的问题，无论多严重都不在本仓库修。

| 归属 | 处理方式 |
|---|---|
| repl-server 自身的代码、契约、文档、审计数据 | 本仓库处理，继续走后面的判定 |
| 外部 MCP server 的响应、上游 API 4xx 的根因 | 记录后转对应仓库，本仓库不代修 |
| 客户端自身行为 | 记录，不在本仓库修 |
| 协议设计内的行为（例如 `server/discover` 只接受 modern 版本） | 只补文档，不改实现 |

## 2. 证据门槛

进入分类前，每条发现必须有可复现证据：

- 日志证据：计数 + 时间点（例如「735 条中 174 条含 X，2026-11-25 02:55Z 一次失败」）；
- 源码证据：`文件:行号`；
- 告警证据：`memory_warning`、`report`、`protocol_dropped`、`payloadDropped`、`tool_test` / `script_saved` 失败等事件，和请求失败一样是发现来源。

只有推测、没有观测或复现路径的，直接归 `INVESTIGATE`，补到证据后再分类。

## 3. 五类判定

| 分类 | 定义 |
|---|---|
| `FIX` | 契约/文档与实现不一致且已造成真实失败；审计数据丢失；安全或数据正确性问题；协议兼容性拒绝真实客户端；核心功能不可用。 |
| `IMPROVE` | 在本仓库、低风险、有测试、可改善可诊断性或使用效率，且不改变外部契约。 |
| `DOCUMENT` | 行为本身是设计内或已修复，但文档缺失/误导。 |
| `IGNORE` | 根因在外部仓库、无实际收益，或维护成本大于收益；必须写理由。 |
| `INVESTIGATE` | 证据不足，先补观测或复现，不直接改。 |

`INVESTIGATE` 必须同时写明观测手段和检查点，不能只写「待观察」。

## 4. 成本不是理由

改动小、几分钟能做完，不构成做的理由。进入 `FIX` / `IMPROVE` 的依据只能是实际损害（有证据）或明确收益（可量化）；`DOCUMENT` 只在文档缺失已经导致实际误用或接入失败时成立。评估时先问「不做会损失什么」，答不出来就归 `IGNORE`。

## 5. 直接改的授权边界

`FIX` / `IMPROVE` 同时满足以下全部条件时，可以直接改代码、测试或文档并跑验证：

- 改动在本仓库内；
- 有第 2 节要求的可复现证据；
- 改动带测试；
- 不破坏外部契约；
- 不引入新依赖；
- 单次可回滚。

以下操作即使改动本身符合上述条件，也必须先问用户：

- commit、push；
- 重启 live 服务；
- 跨仓库改动；
- 数据迁移。

不满足直接改条件的（含 `DOCUMENT`、`IGNORE`、`INVESTIGATE`）只报告，不动手。

## 6. 台账

每次分析结束后，把每条发现写进 `docs/triage-log.md`：

- 一节一个来源，写日期 + 来源，下面是表格：问题 / 分类 / 证据 / 决策 / 理由 / 状态。
- 同类问题先查台账：已判 `IGNORE` 的，除非出现新证据，不再重复提出。
- 状态变化（例如 `待修` → `已修`）时更新原行，不追加重复行。
